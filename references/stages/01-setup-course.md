# setup-course：O 来源约定与 A 模块方案

## 输入与边界

确定课程、根目录、允许与排除的材料、正式知识点目录、代理工作目录和主要用途。按 [storage-policy.md](../shared/storage-policy.md) 核对 Vault、展示目录和库外工作区的实际路径及扫描排除项。废弃稿不读取；混有其他课程的材料先判归属，关键不明项请用户澄清。

嵌入已有课程时读取 [existing-course-integration.md](../shared/existing-course-integration.md)，保护原规划、学习进度和其他阶段成果。材料盘点只记录身份和可读状态，不能替代来源用途确认。

## 初始 O

读取 [evidence-policy.md](../shared/evidence-policy.md) 和 [capability-confirmation.md](../shared/capability-confirmation.md)，按其中流程交付来源策略文件及聊天简报。未明确通过 O 时只讨论来源策略，不提交最终 A 架构，也不预先细化全课程能力或知识点取舍。

## O 通过后的 A 设计

1. 读取当前有效 O，对允许材料作足够的结构扫描，识别章节主题、主要任务类型及依赖。此扫描服务于模块设计，不提前解完全部练习或完成各章编写决策。
2. 建立材料—模块对应关系。一个文件可以支持多个模块，多个来源也可以共同支持一个模块；映射到可定位的章节、页段或题组。O 规定材料怎样使用，A 说明这些材料如何组织成学习单元。
3. 依据核心问题、知识依赖与实际任务设计模块、顺序和接口。说明相对教师结构的保留、合并、拆分或调序理由；不按课件页码机械切章，不把练习顺序直接变成知识主线。
4. 每模块选择唯一主导适配器或 general，确定正式文件分工、命名和必要链接。具体解释属性、局部标题、详略、证明和图文关系留到本章分析；A 不产出逐知识点纳入/省略清单。
5. 首次 B 直接使用 A 顺序中的第一个知识点模块，使审阅同时完成真实学习。说明首模块能够验证的内容和未涉及的知识类型，不为扩大代表性要求用户提前读后续章节。用户明确指定其他模块时遵从；旧项目保留已确认样稿。
6. 使用 [course-context.template.md](../../assets/course-context.template.md) 保存 A-v1 草案，引用有效 O；批准前 active_a_version 为 none，不复制来源策略或另建能力模型。

## A 的文件与聊天交付

按 [双路交互规则](../shared/checkpoint-interaction.md) 区分讨论、待确认和已确认。阶段文件为 `course-context.md`，至少包含：

- 简短的整体主线和组织依据；
- 模块地图：模块/核心问题、对应材料范围、前置接口、划分和排序理由、主导适配器；
- 正式知识点文件分工及必要的外部只读接口；
- 第一模块作为 B 样稿的安排和验证局限；
- 会影响架构的未决事项、受保护成果及必要路径指针。

每个主要划分说明“为何放在一起、为何在此处分开、为何按此顺序”，理由连接材料或学习任务，不能只写“方便学习”。区分可见材料事实与架构设计判断；有实质争议时说明替代方案，不给每项普通选择制造备选清单。

### A 聊天模板

首次提交、重大修订和整体确认使用以下栏目；普通讨论按双路交互规则简化。填写实际内容，不照抄提示。

```text
本轮类型：首次建立 / 后续更新
当前状态：讨论中 / 待确认 / 已确认
方案文件：[架构方案链接]
架构版本：当前有效版本；候选版本（如有）

1. 模块安排
简化模块顺序和主要材料对应关系；注明所据有效 O。

2. 划分与排序理由
解释关键合并、拆分、前置关系及顺序安排。

3. 文件分工与阶段影响
首次：文件分工、首模块 B 安排及验证局限。
后续：文件/模块映射的变化及对后续任务和既有 B 的影响。

4. 待决事项与下一步
实际分歧、确认对象和生效范围；首次按授权衔接 B，后续默认结束。
```

完整映射留在文件中，聊天不只贴目录，也不罗列无助于决定的路径。不逐标题或逐知识点详略审批。反馈同步回阶段文件，重要限制两处一致，只确认一次整体架构。

首次 A 未批准时停在方案讨论；批准后将 A-v1 标为活动版本，记录确认依据、时间、生效起点和所据 O。有首次 B 授权时继续，无授权时询问是否进入 B，不重复索要已有许可。A 获批不免除后续逐章分析责任。

## 用户主动发起后续 A

1. 读取当前有效 O、原有效 A、现有 B 及批次进度/保护边界，再扫描用户指定的新增或更新材料。只在有效 O 允许的用途与范围内设计；需改变来源策略时指出冲突，不在 A 中自行替代 O。若用户同时授权 O/A，先确认 O 更新，再继续 A。
2. 对比材料—模块映射、模块边界、顺序/依赖及文件分工，提出受影响部分的草案。说明“新依据 → 原架构 → 候选架构 → 影响与适用起点”。沿用稳定模块 ID，确需拆分/合并时保留旧新对应，避免把已完成模块误记为未完成或重复生成。
3. 待确认方案写入 `course-context.md` 的候选区；只改候选区，保留活动地图、模块原发布路径、发布记录与当前恢复点。聊天标明“后续更新”，重点解释保留与修改，不重新安排首次 B 模块或更换已确认样稿。
4. 人机讨论确认后合并为下一版活动 A，记录确认依据/时间、所据 O、生效范围和简要历史。明确、完整的架构调整指令可作为对应确认，不连带批准代理补充方案。仅核对且架构不变时记录结果，不强行升版。
5. 更新默认从下一任务或用户指定的未完成任务生效，不自动移动、改名、重写、删除旧章或回写其历史架构版本；这些动作须另行授权。既有完成状态保持原身份，必要时记录与新模块的对应。
6. 重启默认独立结束，不自动进入 B、换样稿或开始批量生成；明确授权联动时才继续。与 O/B、当前任务或前置关系有实质冲突时说明并暂停受影响任务，不宣布全课所有确认失效。

## A 的版本记录

`course-context.md` 维护一份活动架构、待确认修改和简要历史；材料清单/读取状态更新不等于架构获批。活动架构至少记录 A 版本、确认状态与依据、时间、生效起点和所据 O；候选记录原版、新依据、拟变更和影响。生成/审修记录实际使用的 A 版本，不因新版反写旧章。

## 已有项目

已有 O/A/B 按兼容规则沿用。升级不回滚架构、不强制更换样稿；后续 O/B 更新不自动触发 A。旧 A 缺版本号时读取为 legacy，保留可见批准依据，不补造 A-v1 或历史时间；下一次获授权更新时建立版本记录，不因缺字段重做确认。缺失信息影响架构可靠性时只核查相关项。
